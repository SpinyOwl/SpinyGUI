# Browser/native comparison analysis

Analyzed run: `run-18295419870537634196`. All 15 captures completed; all failed the combined geometry/pixel gate. Percentages below mean pixels exceeding the configured channel difference of 16, not the percentage of the layout that is incorrect. Geometry tolerance is 1 px; allowed differing pixels are 0.5%.

Evidence: paired screenshots, saved case definitions and geometry/result JSON, current source, and a disposable native layout probe. No production fixes were made. The probe and log are under `spinygui.visual-tests/build/analysis`. These are static initial-state comparisons: they do not establish hover, transition, editing, or action behavior.

**Shared causes, with source evidence**

1. **Normal-flow block margins are missing.** [BlockLayout.layout](G:/Programming/workspace_idea/SpinyOwl/SpinyGUI/spinygui.core/src/main/java/com/spinyowl/spinygui/core/layout/impl/BlockLayout.java:69) initializes padding and borders but does not resolve the element's margins into its box. The normal-flow path subsequently reads those zero margins; [finishBlockFlow](G:/Programming/workspace_idea/SpinyOwl/SpinyGUI/spinygui.core/src/main/java/com/spinyowl/spinygui/core/layout/impl/BlockLayout.java:193) advances by the border box without a bottom margin. The probe confirms resolved margins of 20 px and 12 px while the corresponding box margins remain zero. Flex item margins are a separate Yoga path and can work; the focused layout fixture's 16 px gap is preserved. Flex containers themselves still pass through block layout.

2. **The geometry comparison assumes DOM semantics that native metrics do not implement.** [LayoutServiceImpl.updateScrollAndClientSize](G:/Programming/workspace_idea/SpinyOwl/SpinyGUI/spinygui.core/src/main/java/com/spinyowl/spinygui/core/layout/impl/LayoutServiceImpl.java:84) derives client sizes from the content box, omitting padding. Its scroll extent starts at zero, excludes absolutely positioned children, and is not floored at the visible extent. Empty native elements can therefore report zero scroll width/height despite matching painted bounds. Browser client dimensions include padding and browser scroll dimensions represent the scrolling area; see [CSSOM View](https://www.w3.org/TR/cssom-view/). [Geometry](G:/Programming/workspace_idea/SpinyOwl/SpinyGUI/spinygui.visual-tests/src/main/java/com/spinyowl/spinygui/visual/Geometry.java:1) directly compares the two APIs. This is a contract mismatch, so a geometry failure does not automatically mean misplaced rendering.

3. **Headless scrollbar policy differs.** [CompareViewsMain](G:/Programming/workspace_idea/SpinyOwl/SpinyGUI/spinygui.visual-tests/src/main/java/com/spinyowl/spinygui/visual/CompareViewsMain.java:40) launches headless Chromium. The installed Playwright 1.58.0 Chromium launcher adds `--hide-scrollbars` in its headless branch; native still paints scrollbars. This is a comparison-harness problem. The focused native scrollbar is 12 px, reducing a 254 × 194 inner area to 242 × 182. The overflow demo also supplies real `::-webkit-scrollbar` styles, so incorrect selector spelling is not the cause. A fair rerun needs an explicit shared scrollbar visibility and size policy.

4. **Numeric font weight and length-valued line height are rejected.** [FontPropertyProvider](G:/Programming/workspace_idea/SpinyOwl/SpinyGUI/spinygui.core/src/main/java/com/spinyowl/spinygui/core/style/stylesheet/property/FontPropertyProvider.java:90) accepts font-weight identifiers but numeric CSS weights are parsed as numeric terms. Its line-height validator accepts normal or a unitless number, not a length such as 24 px. The live probe resolves `font-weight:700` to weight 400 and `line-height:24px` to 1.2. Bold font resources exist. Additionally, [FontServiceImpl.measureFontMetrics](G:/Programming/workspace_idea/SpinyOwl/SpinyGUI/spinygui.core/src/main/java/com/spinyowl/spinygui/core/system/font/impl/FontServiceImpl.java:911) takes the maximum of requested and intrinsic font line heights and rounds metrics in this backend. A requested 20 px control line is 21 px natively. Remaining glyph-edge differences have not been individually isolated from rasterization.

5. **HTML defaults and intrinsic control sizing differ.** [DisplayPropertyProvider](G:/Programming/workspace_idea/SpinyOwl/SpinyGUI/spinygui.core/src/main/java/com/spinyowl/spinygui/core/style/stylesheet/property/DisplayPropertyProvider.java:21) defaults all elements to block. [StyleManagerImpl.userAgentRulesets](G:/Programming/workspace_idea/SpinyOwl/SpinyGUI/spinygui.core/src/main/java/com/spinyowl/spinygui/core/style/manager/StyleManagerImpl.java:338) adds limited form-control defaults, not Chromium's complete HTML stylesheet; a plain span remains block natively. The shared comparison reset does not normalize browser control appearance, borders, text alignment, or resize affordances. [FlexLayout.applyAutoAxisSizes](G:/Programming/workspace_idea/SpinyOwl/SpinyGUI/spinygui.core/src/main/java/com/spinyowl/spinygui/core/layout/impl/FlexLayout.java:188) supplies Yoga with the already-laid-out block width for non-stretched auto-width column items, explaining full-width labels where browser flex items shrink to their text. These differences require a decision between HTML compatibility and explicitly styling paired fixtures.

6. **Fractional grid tracks distribute space incorrectly for this minmax case.** [GridLayout.resolveTracks](G:/Programming/workspace_idea/SpinyOwl/SpinyGUI/spinygui.core/src/main/java/com/spinyowl/spinygui/core/layout/impl/GridLayout.java:199) subtracts a flexible track's minimum as fixed space, then adds its fractional share to that minimum. For 392 px content width, 18 px gap and `2fr minmax(112px, 1fr)`, native calculates 174.67 / 199.33 px. Browser calculates 249.33 / 124.67 px; the second track already exceeds its minimum. The native calculation should not add 112 px on top of an independent 1fr remainder. [GridLayout.reflowItemContents](G:/Programming/workspace_idea/SpinyOwl/SpinyGUI/spinygui.core/src/main/java/com/spinyowl/spinygui/core/layout/impl/GridLayout.java:306) also reflows children directly after final sizing; the direct text layout path bypasses the normal inline-formatting wrapping pass, contributing to clipped text in the narrowed cell.

7. **Border painting uses the top edge for the entire rectangle.** [NvgBorderRenderer](G:/Programming/workspace_idea/SpinyOwl/SpinyGUI/spinygui.core.backend.lwjgl.nanovg/src/main/java/com/spinyowl/spinygui/core/backend/renderer/lwjgl/nanovg/NvgBorderRenderer.java:18) uses top border style, thickness and color, and calls the rectangular stroke overload without corner radii. This explains the uniform red asymmetric border and square green outline. The rounded fixture's resolved radius is correctly 18 px, confirmed by the probe: the value is not rejected by the parser. Background rendering has a radius-aware path, so it would be inaccurate to say every NanoVG shape lacks rounding support.

8. **Transform-origin keywords are rejected.** [TransformPropertyProvider.isCenter](G:/Programming/workspace_idea/SpinyOwl/SpinyGUI/spinygui.core/src/main/java/com/spinyowl/spinygui/core/style/stylesheet/property/TransformPropertyProvider.java:55) only accepts length terms. `left top` therefore leaves the default 50%/50% origin. With a 220 px box scaled by 1.25, that creates the observed 27.5 px left shift relative to a top-left origin.

9. **Programmatic scrolling does not clamp until layout.** [Element.scrollTop/scrollLeft](G:/Programming/workspace_idea/SpinyOwl/SpinyGUI/spinygui.core/src/main/java/com/spinyowl/spinygui/core/node/Element.java:293) assigns the requested offsets and invalidates transforms, whereas clamping occurs in the layout metrics pass. [NativeCaptureMain](G:/Programming/workspace_idea/SpinyOwl/SpinyGUI/spinygui.visual-tests/src/main/java/com/spinyowl/spinygui/visual/NativeCaptureMain.java:77) sets the offsets and prepares another frame, but that transform-only update does not execute layout. The live probe records 10000/10000 with `layoutExecuted=false`; explicitly invalidating layout then clamps to 258/238. Browser clamps to 246/226 because its hidden scrollbars leave a larger viewport. This is a core setter/lifecycle mismatch exposed by the harness's DOM-like assumption.

**Recommended sequence**

First make scrollbar policy and root/control defaults explicit in the harness, and resolve the scroll setter/clamping contract. Then separate border-box mismatches from client/scroll API mismatches in reporting. Fix block margins and font-value handling next because they affect many cases; follow with grid track sizing/text reflow, transform-origin keywords, and border painting. Rerun after each group. Only then isolate remaining text rasterization differences and assess tolerances.

This analysis explains the major observed discrepancies; it does not claim that every differing glyph pixel or small residual metric has been individually attributed. No thresholds were relaxed and no production source was changed during the analysis.
